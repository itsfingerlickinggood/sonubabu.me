Indirect prompt injection and authority confusion

Retrieved content is data. What happens when an application lets it act like an instruction?

Method
Threat modeling and qualitative case analysis

In brief

This qualitative report examines how retrieved text can be mistaken for instructions. The diagrams separate content, authority, and tool effects. They explain a threat model and proposed evaluation design, not a measured attack-success rate or a validated defense.

Why this is a systems problem

A language-model application often combines several kinds of text in one context: developer policy, a user request, retrieved passages, uploaded files, tool output, and prior messages. Humans may understand that a sentence inside a PDF is merely content to summarize. A model sees another token sequence—and may treat imperative language inside it as actionable.

The vulnerability does not require a model to “break” a formal instruction hierarchy in one dramatic step. The system can fail gradually: soften a constraint, adopt a false role, expose a hidden field, call a tool with attacker-chosen arguments, or partially follow an embedded request while claiming to refuse it.

Threat model

The attacker controls content in a source the application is expected to ingest. The attacker does not need direct access to the system prompt or user account. Their content may arrive through a webpage, email, issue tracker, shared document, retrieved knowledge base, or output from another agent.

A useful security invariant is: no text can gain authority merely by claiming it. Authority must come from a trusted channel, an authenticated principal, and an application-side policy decision.

Qualitative failure patterns

Instruction–data conflation

Quoted or retrieved content is followed as though it came from the controlling user. Formatting alone—quotation marks, delimiters, or a “document” label—does not guarantee separation.

Authority transfer

Untrusted text claims to be a system message, administrator note, updated policy, or tool instruction. The model treats the role claim as evidence of authority rather than as attacker-controlled content.

Partial compliance

The model may reject the most obvious embedded instruction while still disclosing a requested detail, changing the summary, omitting information, or preparing a tool call influenced by the injection. A binary “refused injection” label can miss these partial effects.

Context laundering

An untrusted instruction can be paraphrased by one component and passed to another without its original provenance. The downstream model receives clean-looking text whose trust history has been erased.

Tool mediation

A model does not need to reveal sensitive text directly to cause harm. It can search for attacker-chosen terms, send a message, modify a file, or construct API arguments. Tool execution turns language-level confusion into a state change.

Why tools raise the stakes

In a text-only chatbot, the immediate output is usually visible to the user. In an agentic workflow, the model may act through capabilities the user cannot fully inspect. The security boundary must therefore sit between model proposals and executable operations.

Low-consequence transform

Summarization can still be manipulated, but the effect is bounded when no secrets or external actions are available.

Privileged action

Email, file, payment, deployment, or identity operations require deterministic authorization and explicit scope.

Inspectable proposal

The model produces a typed action plan that can be checked before execution.

Opaque execution

Free-form model text flows directly into a shell, browser, or API without validation.

Defense in depth

No single prompt can establish a complete security boundary. A stronger design combines provenance, least privilege, deterministic checks, and regression testing.

1 · Label
Attach origin, trust level, and owner metadata to every retrieved chunk and tool result.
2 · Separate
Represent policy, user intent, untrusted data, and tool schemas as distinct typed fields where the platform permits.
3 · Constrain
Expose the minimum tools and arguments required for the task; use allowlists and scoped credentials.
4 · Authorize
Validate permissions and high-impact actions in application code, not only in model reasoning.
5 · Verify
Inspect proposed actions, resulting state, and output for policy violations; require confirmation when consequences are material.

How to evaluate it

A useful benchmark should vary both the injection and the system capability. The same document may be harmless in a summarizer and consequential in an agent with email and file access.

  1. Create benign and adversarial document pairs that preserve the user’s visible task.
  2. Vary injection placement, formatting, language, role claims, and retrieval rank.
  3. Run with fixed model, decoding, system policy, and tool permissions.
  4. Record generated text, proposed tool calls, executed actions, and final external state.
  5. Score task completion, policy adherence, unauthorized action rate, and false positives on benign content.
  6. Publish attack strings only at a level appropriate for responsible security disclosure.

Evidence boundary

What this report is

A qualitative security analysis that clarifies trust boundaries, failure observables, and evaluation design. It is not a benchmark result or an estimate of real-world attack success.

The source report does not contain a representative dataset, attack-success percentage, confidence interval, or controlled defense comparison. The schematics show the proposed failure mechanism; they are not captured attack traces. Defense effectiveness remains a question for controlled testing.
